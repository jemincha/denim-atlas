# Project working rules

Use the user's current instructions and the approved research scope in
`docs/SPRINT_REVIEW.md`. Read `PROJECT_STATE.md` and the latest sprint review
before resuming work. Historical setup documents are not current status.

Present human comparison images in right-side Codex tabs so the researcher can
inspect/zoom them while typing in chat. Do not embed the comparison boards in the
chat by default. A queued tab request is not confirmation that it is visible.

At every sprint boundary, including a user-requested safe stop:

- Compare actual progress with the approved flow: permitted data -> garment/region
  preparation -> grouped splits -> axis-specific supervision -> adaptation ->
  independent comparison -> error analysis and the next experiment.
- Separate working code, training-set fitting, development findings and unseen
  matching-quality evidence. Do not substitute counts of commits/tests for quality.
- Record remaining limits, regressions, deviations and unresolved external feedback.
  For each material gap name the next investigation, evidence needed, and the
  decision it would change. Investigate within existing authorization; brief the
  user before changing research direction or when human evidence/access is needed.
- Append a compact review to `docs/SPRINT_REVIEW.md`, update `PROJECT_STATE.md`,
  and update README only when its public snapshot changed. Keep raw judgments,
  correspondence, images and operational logs private.
- Brief the user in Korean: target vs actual progress; evidence and limitations;
  what will be investigated or changed; the next concrete work and any required
  human intervention. Keep the quality-first comparison against a strong general
  multimodal model explicit. Do not promise superiority without matched evidence.

Continue through routine authorized steps until a real human gate. A review is
not permission to end every completed subtask or to create recurring automations.
